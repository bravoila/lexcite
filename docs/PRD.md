## 1. 背景与目标

1.3.2 已实现混合 RAG、有状态研究循环、引用校验、案件记忆等核心能力,测试与文档质量高。本轮审查发现**若干会直接影响法律结论正确性与部署安全的缺陷**,以及产品向规模化演进的结构性缺口。

**1.4.0 的目标:先把「会出错」的修掉,再把「能上生产」的补上。**

具体分三层:
1. **P0 正确性/安全阻塞项**:修复会让错误法条通过校验、或让攻击者影响全员可用性的缺陷。
2. **P1 安全加固与工程健壮性**:补齐部署安全基线、导入解析可靠性与后台任务状态机。
3. **P2+ 产品能力**:评测体系、多租户、可观测性等面向真实业务的演进。

**非目标(本期不做)**:百万级文书搜索引擎、Book-to-Skill 蒸馏、真实法律准确率承诺、模型微调。

## 2. 优先级总览

|---|---|---|---|

## 3. P0:正确性与安全阻塞项

### P0-1 登录限流按身份隔离,禁止匿名锁死全员

**现状**:`app/auth.py:48-54` 以 `request.client.host` 为限流键;`Dockerfile:15` 以 `--no-proxy-headers` 启动,反代部署时所有用户共享代理 IP。任何匿名者连续 10 次错密码,全员(含管理员)10 分钟无法登录,且可反复触发。

**需求**:
- 限流键双层:账号(或账号+IP)+ 全局匿名请求限额。
- 反代场景支持 `--proxy-headers --forwarded-allow-ips`,仅信任已知代理的 XFF。
- 管理员账号免于被全局限额锁死(或提供本地恢复通道)。

**验收标准**:
- [ ] 反代部署下,匿名者用错误密码撞库 30 次,不影响正确密码登录。
- [ ] 单账号 10 次失败仍触发该账号 10 分钟限流。
- [ ] `docker compose logs` 中不出现因 XFF 伪造导致的错误限流。

### P0-2 模型密钥与端点绑定,端点变化即失效

**现状**:`app/llm.py:107-115,131-140`。API 请求省略 `api_key` 字段时,旧密文无条件保留;修改 `base_url` 后旧云端密钥仍会发往新端点,构成密钥外泄路径。检索/搜索服务密钥需同步检查(`app/websearch.py:43-53` 已实现正确模式,可作为参照)。

**需求**:
- 密钥与 (profile, provider, base_url) 三元组绑定;任一变化即清除已存密钥。
- 空字符串与省略字段行为一致(不再区分)。
- 保存前对 base_url 做安全校验(见 P1-2)。

**验收标准**:
- [ ] 保存 base_url 为新值且不带 api_key 字段 → 旧密钥不随新端点发送。
- [ ] 测试连接/研究调用时,`resolved()` 返回的密钥只来自与当前端点匹配的存储项。
- [ ] 增加回归测试覆盖「改地址后密钥外泄」场景。

### P0-3 修正轮检索词不再被截断丢弃

**现状**:`app/engine.py:305`。模型修正查询 `plan.queries` 拼接在 needs 展开之后,`[:9]` 截断。needs 累计 ≥7 条时修正查询全部被丢弃,第 2/3 轮只能重复旧检索。

**需求**:
- `plan.queries` 置于 needs 展开之前,或为修正查询单独预留名额。
- 检索查询预算(去重后上限)在日志/进度中可核对。

**验收标准**:
- [ ] needs=8 且 plan.queries=3 时,第 2 轮实际检索包含至少 2 条修正查询。
- [ ] 新增单测:多法源场景下第二轮检索词集合 ≠ 第一轮。

### P0-4 条号精确匹配必须绑定法规主体

**现状**:`app/retrieval.py:172`。`len(unique_laws)==1` 时,查询中任意「第N条」都成为该法精确命中。仅导入《民法典》时问「刑法第264条」,民法典第 264 条被置顶。

**需求**:
- 查询点名其他法规(即使该法规未入库)时,禁止无主体条号匹配。
- 仅当查询未点名任何法规、或点名法规与候选同法规时,条号才可精确加分。
- 未入库法规的点名应转为「缺少法源」提示,而非错误召回。

**验收标准**:
- [ ] 单法库(民法典)下问「刑法第264条」→ 民法典 264 条不得进入精确匹配通道。
- [ ] 新增单测覆盖「点名他法 + 单法库」场景。
- [ ] 回答先保留现有资料能支持的结论，再显示「推荐补充资料:刑法」，不得错误引用其他法律。

### P0-5 条号/法规名比较统一规范化(article_key / law_key)

**现状**:`app/engine.py:62-69`、`app/retrieval.py:236-238` 使用原始字符串全等比较。导致:
- 正文「本法第一百二十三条」与标题「第123条」不一致时,同法引用展开漏召回。
- 裸名称「民法典第五百七十七条」(无书名号)可引用同号他法条文通过确定性校验。
- 「第134条之1」(阿拉伯数字+之)解析失败。

**需求**:
- 所有条号比较(引用校验、同法展开、`之`后缀)统一经 `ingest.article_key` 规范化。
- 法规名匹配支持《》剥离后的裸名称,与法库 `law_key` 对齐。

**验收标准**:
- [ ] 标题「第123条」+ 正文「本法第一百二十三条」→ 展开命中。
- [ ] 引用「民法典第五百七十七条」→ 只能匹配民法典第 577 条,不匹配他法。
- [ ] 「第134条之1」→ 识别为独立条号。
- [ ] 上述场景各有一条回归测试。

### P0-6 覆盖检查异常时,检索结果变化必须强制清空旧结论

**现状**:`app/engine.py:349-358`。CoverageAudit 异常时 `continue` 跳过「ids 变化即清空 claims」分支,旧批准结论可能与未复核的新证据一起返回。

**需求**:
- 检索候选 ID 集合一旦变化,已批准 claims/citations 立即失效,重新走校验流程。
- 异常路径与正常路径共用同一失效逻辑,不依赖覆盖检查成功。

**验收标准**:
- [ ] 首轮通过 → 次轮新增候选且覆盖检查抛异常 → 回答不包含首轮未校验过的结论。
- [ ] 新增单测:模拟 CoverageAudit 异常 + 候选变化。

## 4. P1:安全加固

### P1-1 会话 Cookie 安全默认

**现状**:`app/main.py:121` Secure 默认关闭。HTTP 内网部署或反代漏配时密码与会话可被嗅探。

**需求**:`LEXCITE_PUBLIC_URL` 为 https 时强制 Secure;以 http 启动且非 loopback 绑定时打印告警;部署文档补充 HSTS 配置。

**验收**:PUBLIC_URL=https 且 LEXCITE_SECURE_COOKIE=0 → Cookie 仍带 Secure;告警可见于日志。

### P1-2 模型/检索/搜索端点 SSRF 防护

**现状**:`app/models.py:91-99` 仅拉黑两个元数据主机,127.0.0.1、内网段、链路本地(169.254.x、100.100.100.200)均放行;「测试连接」可探测内网,`app/llm.py:291` 回显错误 JSON 构成半盲 SSRF。

**需求**:解析 base_url 后拒绝私有/回环/链路本地/元数据网段;连接钉扎解析后 IP;本地 Ollama 走显式白名单(host.docker.internal / ollama 服务名)。

**验收**:base_url=http://127.0.0.1:9000、http://169.254.169.254 等 → 保存被拒绝并给出原因;白名单内地址可保存并测试。

### P1-3 鉴权前不再缓冲大请求体

**现状**:`app/main.py:50-62` 未登录 POST 也可反复提交 22MB 包耗尽单 worker 内存。

**需求**:鉴权失败时提前断开(413/401 优先于 body 解析);体上限从 22MB 降至合理值(如 8MB,法条文本走流式或分片);文档建议反代限制并发与 body。

**验收**:未登录 POST 大包 → 401 且不触发完整 body 解析(用 Content-Length 预判)。

### P1-4 数据文件权限收紧

**现状**:`app/db.py:20-28` 数据目录 0755、SQLite 0644;直接 Python 部署且主机多用户时案卷可被他人直读。

**需求**:数据目录 0700、DB/WAL/SHM 0600;启动时自动纠正既有权限;`secret.key` 保持 0600。

**验收**:`ls -l data/` 与 `lexcite.sqlite3` 权限符合;多用户主机上非属主读取被拒。

### P1-5 初始化码不出现在 stdout

**现状**:`app/auth.py:34` 初始化码打印到 stdout,未初始化期间每次重启重印;能读日志者可在管理员之前抢占初始化。

**需求**:初始化码写入一次性文件(已 0600),从日志移除;改为首次部署时提示「初始化码见 data/setup-code.txt」。

**验收**:启动日志不含初始化码;文件读取后流程不变。

### P1-6 Origin 白名单不依赖 Host 头

**现状**:`app/main.py:44-49` Origin 白名单由 Host 头推导且未校验 Host;反代透传任意 Host 时可绕过。

**需求**:白名单以 `LEXCITE_PUBLIC_URL` 为固定来源;Host 头与 PUBLIC_URL 不符时拒绝或忽略 Origin 校验走 SameSite 主防线。

**验收**:伪造 Host 头的跨站请求仍被 SameSite=Strict + 自定义头拦下;测试覆盖。

### P1-7 前端链接渲染仅允许 http/https

**现状**:`static/app.js:107` 搜索结果 URL 经 `esc()` 后直接渲染为 `<a href>`,未校验 scheme;`javascript:` URL 点击即执行,可窃取会话。

**需求**:渲染前校验 `new URL(...).protocol` 为 http/https;非 http(s) 降级为纯文本并保留来源标题。

**验收**:构造 javascript: 协议的搜索结果 → 页面显示为不可点击文本。

## 5. P1:导入/解析可靠性

### P1-8 章节标题不污染条文正文

**现状**:`app/ingest.py:90`「第二章合同的订立」等无空格章节行残留进上一条正文,污染全文检索与引用。

**需求**:章节/分编行独立识别并从 body 剔除,记录 `heading_path` 元数据。

**验收**:导入含章标题文本 → 条文正文不含章节行;预览可核对。

### P1-9 拆条启发式疑似误并时阻断预览

**现状**:`app/ingest.py:42-57,75-80` 引用启发式可把真实条标题(如「第二条 正文」)吞进上一条。

**需求**:后文为清晰条号模式时优先按条号断;疑似误并的边界在预览中给出显式告警,要求人工确认。

**验收**:构造「…依照下列规定\n第二条 …」用例 → 拆分正确或出现阻断告警,不静默合并。

### P1-10 SHA256 可审计

**现状**:`app/ingest.py:118-127` 只存哈希不存原文快照,且哈希对象与入库内容不一致(GB18030/BOM/CRLF、说明段截断),引用卡片 SHA256 无法对账。

**需求**:保存压缩原文快照;统一哈希对象(声明:对入库后规范化正文计算);引用卡片提供重算入口。

**验收**:对同一导入,卡片 SHA256 可由存档重算一致;文档明确哈希口径。

### P1-11 PDF/DOCX 静默丢失防护 + 解析移出事件循环

**现状**:`app/ingest.py:149-160`、`app/main.py:340-347`。扫描页/表格/页眉内容静默丢失;大文件在 async 端点同步解析阻塞全站。

**需求**:按页空文本比例、耗时、字符上限拒绝可疑文件并给出原因;解析移入线程池;DOCX 合并表格/页眉页脚。

**验收**:20MB 扫描 PDF → 明确报错而非入库缺条;上传期间其他请求延迟不显著上升。

### P1-12 联网阻断复用复核截止与辖区判定

**现状**:`app/authorities.py:222-224` 阻断只查 `reviewed_at` 真值,不套用复核周期与辖区,可能误阻断官方原文。

**需求**:复用 corpus 的 cutoff/辖区判定;不满足阻断条件时降级为 warning。

**验收**:本地同名版本复核已过期 → 联网补查不再被误阻断。

### P1-13 重复导入查重

**现状**:无内容级去重,重复导入仅返回泛化 409。

**需求**:按 (canonical_name, version, jurisdiction) 或正文 SHA256 查重,返回已有记录 ID 与提示。

**验收**:同正文重复导入 → 返回「已存在法规 X」而非 409。

### P1-14 Markdown 结构标记兼容

**现状**:`app/ingest.py:135-141`「## 第一条…」「**第一条**…」行首标记使条标题无法识别。

**需求**:提取时剥离行首 `#`、`*`、`-` 结构标记;补测试。

**验收**:Markdown 文件导入拆条数与纯文本一致。

## 6. P1:工程健壮性

### P1-15 索引任务取消竞态终态化

**现状**:`app/indexing.py:196-215`。线程启动前 `_stop` 已置位时,worker 直接退出且不更新任务状态,任务永久 queued,UI 永远显示「等待」。

**需求**:worker 的 finally 对非终态任务强制置 interrupted;提交与启动同锁。

**验收**:提交后立即取消 → 任务最终进入 interrupted/failed,不残留 queued。

### P1-16 研究任务取消检查去数据库化

**现状**:`app/jobs.py:98-101` `cancelled()` 每次新建 SQLite 连接,流式模型每行触发,长思考流可产生上千次查询。

**需求**:内存 Event + 限频落库(如 1s 一次)。

**验收**:取消延迟 < 1s;流式期间 SQLite 查询次数与行数无关。

### P1-17 检索全表扫描下推与缓存

**现状**:`app/retrieval.py:84-107` 每轮至少 3 次全表取 laws/articles 再 Python 过滤。

**需求**:SQL 按 law_id/日期/辖区过滤,单次查询缓存复用。

**验收**:法库 5000 条时单轮检索 SQLite 读取行数明显下降(基线对比)。

### P1-18 LLM 调用退避重试与墙钟预算

**现状**:`app/llm.py:182-256` 429/5xx/超时立即消耗调用次数,无退避;timeout 仅为单次读超时,SSE 可拖到总时限。

**需求**:限次重试(≤2)并尊重 Retry-After;单次调用受墙钟硬预算约束。

**验收**:模拟 429 + Retry-After: 2 → 自动重试且总时长受控;SSE 挂起 → 到点强制中断。

### P1-19 无新证据时提前结束研究

**现状**:`app/engine.py:406` 联网开启且缺口均已尝试后仍跑满 3 轮。

**需求**:按 collector.attempted 判定无新证据即结束,节省费用与时间。

**验收**:全部缺口已尝试且无新候选 → 第 2 轮结束,不再空转第 3 轮。

### P1-20 模型声明的缺失法源须经服务端判定

**现状**:`app/engine.py:203-208,337-338` `update_gaps` 把模型声称的 missing_authorities 直接加回,即使该法源+条号可用,产生假缺口与多余联网读取。

**需求**:显式项先经 authority_gaps 判定;仅真正缺失才进入缺口。

**验收**:模型误报已存在法源 → 不产生假缺口、不触发联网读取。

## 7. P2:评测与可观测

### P2-1 法律评测集与 CI 门禁

**需求**:
- 标注集扩展为「法规名称+版本+条号」粒度;至少覆盖:缺关键事实、虚构法条、过期法、新旧版本冲突、地区不符、通则与例外、遗漏司法解释、跨法规问题、提示注入、多轮记忆污染(现 `evals/README.md` 已列清单)。
- 建立人工标注保留集(不参与提示词调整),由律师评阅 `human_legal_correctness` 与 `human_citation_entailment`。
- CI 门禁:Recall@20 / MRR@20 / nDCG@10 回归告警;错引率、未支持结论率纳入报告。

**验收**:评测命令一键运行并输出 CI 可解析报告;指标回退自动失败。

### P2-2 调用级遥测

**需求**:记录每次 LLM/向量/重排/搜索调用的耗时、输入输出 token、费用估算、重试次数、http_status,聚合到研究任务与全局仪表。

**验收**:单次研究结束后可查看逐调用账单明细;支持多模型成本对比。

### P2-3 检索质量增强

**需求**:
- 分词归一:法规简称/旧称映射、繁简转换、同义扩展(如「合同解除」→「解除合同」类语序)。
- 维度漂移、复核过期、索引覆盖率从被动提示升级为设置页主动告警。

**验收**:简称/繁体查询召回与全称一致(受控用例);告警在保存配置后 1 分钟内出现。

### P2-4 任务恢复

**需求**:服务重启后 interrupted 任务可手动续跑;续跑前展示将发生的模型调用次数与预估费用并二次确认。

**验收**:研究进行中重启 → 恢复后任务显示「已中断,可续跑」;续跑不重复计费已完成的调用。

### P2-5 备份归档校验

**需求**:备份包带校验和与恢复演练说明;恢复前校验完整性。

**验收**:篡改备份文件 → 恢复被拒绝。

## 8. P2:产品能力

### P2-6 批量导入与进度

## 9. P3:多租户与权限(独立里程碑)

**背景**:当前单密码共享工作空间,同一密码可见所有案件(README、ARCHITECTURE 已承认)。

- **P3-1 用户与角色**:独立用户、管理员/资料员/办案人员角色。
- **P3-2 案件权限**:案件归属、可共享范围、跨用户访问控制。
- **P3-3 审计归属**:审计记录操作者身份;登录成功/失败、导出、删除、设置变更全量记录;防篡改(哈希链或只追加存储)+ 查看入口。
- **P3-4 认证增强**:密码修改与轮换、会话列表与远程注销、MFA/SSO 预留。
- **P3-5 存储加密**:案件内容字段级加密(密钥轮换);当前仅 Fernet 保护模型密钥,且密钥与 DB 同卷。

**里程碑建议**:M1 用户+角色+案件权限 → M2 审计 → M3 认证增强 → M4 加密。

## 11. 发布与验收

1. **回归基线**:现有 209 项 pytest + 59 项浏览器检查全通过。
2. **新增测试**:本 PRD 每个「验收标准」至少一条自动化测试;P0 全部有测试。
3. **真实服务冒烟**:发布前至少完成一次真实国产 API(聊天/向量/重排)+ 本地 Ollama 的端到端验证(1.3.x 验证记录明确未做过,此项为 1.4.0 发布门槛)。
4. **法律评测**:P2-1 保留集跑通并记录指标;不承诺准确率,但报告必须可复现。
5. **安全回归**:SSRF、锁死 DoS、密钥外泄、权限各一项负向测试。

## 12. 风险与边界

- **SSRF 收紧与本地服务冲突**:P1-2 的白名单必须覆盖 host.docker.internal/ollama/reranker 三种既有部署形态,避免修复引入部署回归。
- **密钥绑定迁移**:P0-2 上线时需处理存量已存密钥的迁移(按当前 endpoint 保留或要求重新输入)。
- **法律边界不变**:引用原文匹配与模型复核不保证法律结论正确;评测指标不构成「法律准确率」声明。
- **单进程边界不变**:多租户(P3)落地前仍需单 worker + 线程锁模型,不引入分布式部署。
