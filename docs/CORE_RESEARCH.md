# 核心研究 Agent

法律研究逻辑集中在 `app/research_agent/`，公开入口为 `from app.research_agent import answer`。这是应用内部模块，不是独立服务，不引入新的 Agent 框架。HTTP、后台任务、数据库、模型接口及向量索引仍留在外层，页面 API 和历史结果字段保持兼容。

| 文件 | 职责 |
| --- | --- |
| `runner.py` | 研究编排、修正条件、预算、进度与耗时 |
| `prompts.py` | 分析、复核、事实整理与修正计划提示词 |
| `schemas.py` | 草稿、覆盖、结论、事实与复核数据结构 |
| `context.py` | 有来源的案件事实、多轮上下文与追问去重 |
| `retrieval.py` | 法规身份、日期、地区过滤及混合检索 |
| `authorities.py` | 法源目录、官方原文补查与元信息核对 |
| `verification.py` | 引文 ID、连续原文及法规名称完整性校验 |

## 输入与案件记忆

`research_agent.context` 从用户消息、手工确认事实和有原话来源的快照构建上下文。助手回答和原始思考不作为事实。问题后面的“办了”“没有”等按问答边界关联；原始问答与来源 ID 一并保存。只有上轮只有一个问题时才直接解释孤立短答，否则交给有来源约束的模型整理；歧义仍需核对。

语义整理用于补充、编号回答、更正等场景，不能伪造用户引文，也不能覆盖已准确关联的字面问答。数字/持续时间发生变化或否定冲突时需明确更正。未知保持未知；“未用于抚养子女”不能等同“没有子女”。模型整理仍可能误解复杂主体与时间，因此自动陈述与手工确认分开显示。

最多保留 70 项、18,000 字符的原话事实摘要；另保留最近 12 条、8,000 字符的原始用户消息。语义整理只接收受限的原话窗口。重要事实可手工确认。快照随问题/答案在同一数据库事务提交，刷新或服务重启后保留；运行中取消不提交未完成答案。

## 检索与动作选择

1. 普通问题直接使用研究主题、已有事实和本次问题检索，不固定先调用模型规划。本地先按标准法规身份、地区、日期、复核状态与版本冲突过滤，再做关键词/向量/精确匹配及可选重排。明确指定的条号必须属于同一法规。
2. 若已有目录缺口且开启联网，先查小型官方网址目录；目录外文件用已配置搜索服务查找。自动搜索仅提交通过格式检查的法规名称，绝不自动把案件全文作为搜索词。手工公开词单独发送，请勿填写隐私。
3. 模型一次完成候选相关性、法源覆盖、现有资料分析和推荐补充资料。没有相关证据时结论必须为空，但仍可提出补充建议；部分资料能支持的规则不因缺专项文件而一并放弃。
4. 草稿提出新的法源需求且确实取得新原文时，在同轮内最多再生成一次分析；没有取得新原文不重复生成。官方正文仍须通过 HTTPS/DNS/TLS 防护、名称/文号/施行日期匹配、条号连续性检查；目录外文件另需有原文支持的元信息核对。草案、新闻解读和案例不能替代法条。
5. 官方新文不能悄悄覆盖日期重叠的人工复核版本。临时来源只存本次所引用的完整条文、元信息、读取时间、文本哈希及相关施行条款，不自动导入正式法库。新证据加入会使旧的部分结论失效，重新分析和复核之前不能沿用。
6. 逐项检查引用 ID、连续原文、法规名和条号，再独立调用模型复核支持关系。通过后立即返回已有依据的结论与下方的推荐资料；仅缺资料或个案事实不会触发完整重跑。
7. 引文、输出或支持性检查失败时才进入修正计划，改写检索和分析，仍受轮数与总调用预算限制。相同证据上只能澄清事实或没有候选时停止，不反复要求已提供的信息。只追问最多三个必要新问题。

同一模型的覆盖检查和复核可能同时犯错；这不保证实体结论正确，也不是法律适用已由独立专家复核。

## 预算和兼容性

仍支持 Ollama 和国内兼容 API，未新增模型服务依赖。普通问题通常只有法律分析、独立复核两次核心模型调用。事实整理、官方元信息、追问核对按需增加；最多 3 个分析/修正轮、18 次聊天调用，另受总时限控制，不是默认完整跑三轮。

研究计划、事实分类、追问去重和官方元信息核对，在已知支持的模型服务上按请求关闭思考，修正计划输出上限最多1200 token；自定义接口保留用户配置，避免假定兼容性。法律分析和复核仍遵循用户的思考配置。这些临时参数不会改写保存的设置。

结果新增 `model_runs`，每次调用记录阶段、模型、状态、耗时、请求数据字符数和供应商返回的 token 用量；未返回用量时为 `null`，不估算。前端和导出均可查看。`retrieval_runs` 记录检索耗时，官方补查也有耗时事件。两次调用是流程数量，不是实际延迟或法律准确率承诺。

自动补查最多 2 次搜索、4 次官网读取。手工公开词另限 1 次搜索、2 次读取。默认不联网。内置目录只是 URL/名称/文号/施行日期/条数目录，不含彩礼答案模板，也不是全国法库或持续更新服务。

`AskInput.online_research`：`true` 开启本次官方补查，`false` 关闭，`null` 沿用设置。`source_gaps` 与 `missing_facts` 分别表示法源与案件信息缺口；`candidate_sources` 仅供检索调试，不作为回答引用。临时证据使用 `authority_status=official_auto_checked`，正式复核资料使用 `human_reviewed`。

`analysis_scope=available_sources` 表示结论只基于本次实际取得并筛选的资料。推荐补充资料来自问题匹配的小型目录，以及模型在计划、覆盖检查和草稿阶段提出的正式名称/条号；程序再对照法库检查名称、条文、日期、地区和复核状态。它不是模型直接查看磁盘得出的“缺文件”结论，也不是已核实的穷尽清单；名称、条号和适用性可能有误。未取得正文的建议不会成为引用，页面和导出均将建议放在已有结论之后。覆盖和补充范围检查已合并进法律分析，不再单独增加一次覆盖模型调用。

## 模型效果验收

在已配置模型的部署环境运行：

```bash
python scripts/evaluate_core.py --run-live --online --output core-evaluation.json
```

Docker 默认服务可运行 `docker compose exec lexcite python scripts/evaluate_core.py --run-live --online --output /tmp/core-evaluation.json`，再用 `docker compose cp lexcite:/tmp/core-evaluation.json ./core-evaluation.json` 取出报告。这会真实调用模型，可能产生 API 费用；纯 Ollama 使用本地资源。

脚本新建临时数据库，只复制法律资料和模型/搜索配置，不复制业务案件，不修改正式数据库。它运行“彩礼问题 → 用户原样补充四项事实 → 提醒沿用已知信息”三轮对话，输出事实来源覆盖、研究主题、结论数、专项条文引用和接口错误。不会把同一模型的自我评分当作正确率。报告里的每个法律结论还需法律人员逐项核对一般规则、例外、时间适用、子女信息和返还比例。

## 1.2.2 法源定位修复

正式名称先移除成对的最外层书名号，保留名称内部的引用，再用于目录、公开词和显示；不按相似度把不同法律视为同一部。历史记录的显示和导出也避免重复包书名号。

刑法目录增加整编全文和官方备用入口，校验第一条至第四百五十二条主条号、目录记载的修正案名称及修订时间。另读修正案原文核对2024年3月1日施行日期，在引用中保存日期来源URL、哈希和读取时间。未取得日期依据、不完整正文、旧版本或目录未知的新修正案均不作为临时证据。四次读取预算包含日期核对与失败尝试。主条号连续性不能证明所有新增“条之…”和后续修法均已穷尽，仍须人工核对原文及版本。

目录读取失败后，可在已配置搜索服务时进行一次受限的搜索回退，仍计入两次搜索总预算；同一规范在一次研究中不会重复无效尝试。缺口中保存具体online_state/online_detail，区分search_not_configured、search_limit、read_limit、time_limit、read_failed、search_failed、version_not_covered、not_found。无配置时提供设置入口，不把本地缺口冒充互联网无结果。

## 1.3.0 混合检索升级

向量与重排从聊天地址中独立出来，配置/索引就绪后执行 BM25、向量和精确条号召回，经RRF和重排后进入合并的法源覆盖与法律分析。`retrieval_runs`逐次记录实际方法、覆盖数、请求数与降级原因；完整条文仍是分析和引用校验依据。官网临时全文当前不批量向量化，其检索路径单独标识。详见 [RETRIEVAL.md](RETRIEVAL.md)。

`evaluate_retrieval.py`提供固定法库的三组消融，`evaluate_core.py`同时复制独立检索设置与对应索引运行多轮事实和引用验收；均隔离生产案件，不把合成协议测试当作真实模型正确率。
